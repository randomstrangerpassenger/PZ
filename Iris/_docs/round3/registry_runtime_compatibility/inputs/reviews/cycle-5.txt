## 1. Verdict

# FAIL

Cycle 4 개정본은 이전 검토에서 제기된 다음 문제를 충분히 해결했다.

- roadmap 필수 fixture 1~10의 명시적 traceability
- 일반 key positive fixture
- Windows projection cardinality-loss negative fixture
- exporter/package repository-wide invocation census
- post-adoption canonical default route

- governance-only ledger bootstrap commit
- single integration branch와 event-prefix equality
- record/event/VCS/shared-ledger transaction 순서
- bridge preflight와 post-generation four-surface validation 분리
- roadmap의 OR 조건을 더 강한 AND 조건으로 바꾸는 owner acknowledgement
- content-addressed durable bundle ID
- PUC Lua 검증 상한 명시

따라서 이전 Cycle 4 review의 Critical finding은 계획상 대부분 해소되었다.

그러나 현재 계획에는 다음 세 blocker가 남아 있다.

1. Gate B의 attempt reservation을 수행할 실행기가 implementation entry 이전에 존재하지 않는다.
2. owner-bound exception을 구성하는 owner/review authority record가 durable bundle과 live required surface에 포함되지 않는다.
3. final machine report, independent review, owner seal, final closure report, terminal seal이 disposable local supporting evidence에만 남는다.

이 상태에서는 implementation entry와 canonical closeout 중 적어도 하나가 성립하지 않는다.

## 3. Critical Issues

### Issue RTC-C5-1 — Gate B Attempt Reservation Executor Bootstrap Cycle

**Severity:** Critical

**Impact:**

계획은 implementation entry 전에 다음을 요구한다.

```text
attempt reservation
reservation record exclusive-create
event ledger append
reservation VCS commit
shared ledger update
attempt_reservation_receipt.json
preimplementation_gate_report.json
```

이 작업에는 다음 기능을 수행할 실행기가 필요하다.

- named mutex 획득
- Git common-dir coordination
- event prefix 검증
- immutable reservation record 생성
- JSONL event transaction
- Git stage/commit
- shared reservation ledger 갱신
- partial-state reconciliation
- Gate B predicate 계산

그러나 이 기능을 수행할 신규 tooling은 `Repository Areas Affected`에 포함된 implementation code다.

```text
run_dvf_3_3_registry_runtime_compatibility.py
dvf_3_3_registry_runtime_compatibility.py
validate_dvf_3_3_registry_runtime_compatibility.py
```

현재 Gate A가 허용하는 bootstrap commit은 다음뿐이다.

```text
ledger_bootstrap_contract.json
zero-byte attempt_events.jsonl
필요한 exact .gitignore exception
```

즉 현재 순서는 다음과 같다.

```text
Gate B reservation executor 필요
→ executor는 아직 구현되지 않음
→ executor 구현은 implementation_entry_allowed 이후
→ implementation_entry_allowed는 Gate B reservation 완료를 요구
```

이는 직접적인 bootstrap cycle이다.

Gate A 문서와 빈 ledger만으로 named mutex·transaction·reservation commit을 machine contract대로 실행할 수 없다.

수동 Git/PowerShell 명령으로 수행할 경우에도 다음 문제가 생긴다.

- reviewed executable identity 없음
- exact command schema 없음
- tool hash 없음
- partial-state handling의 재현성 없음
- toolchain manifest 이전의 unbound code execution

**Affected Scope:**

- Change 0
- Gate A / Gate B
- attempt allocation
- preimplementation gate
- governance bootstrap
- execution provenance

**Related Surface:**

- Authority Surface
- Sealed Artifact Surface

**Required Fix:**

다음 중 하나를 명시적으로 선택해야 한다.

#### Option A — Bootstrap-Only Governance Executor

Gate A에서 다음과 같은 최소 executor를 ledger 파일과 함께 owner-approved bootstrap commit으로 채택한다.

```text
tools/governance/
  reserve_iris_registry_runtime_compatibility_attempt.py
```

이 executor의 책임은 다음으로 제한한다.

- mutex
- event prefix
- reservation record
- event append
- reservation commit
- shared ledger
- Gate B reservation receipt

금지:

- compatibility census
- source/rendered/runtime inspection
- exporter/package modification
- required-validation adoption
- PASS claim

필수 조건:

- plan review가 executor schema와 허용 책임을 승인
- Gate A commit에서 executor path/hash 고정
- bootstrap executor 자체의 test/fixture 존재
- bootstrap contract가 executor hash를 결속
- Gate B가 오직 해당 executor만 사용
- executor 변경 시 bootstrap 재승인

#### Option B — Implementation Setup Gate 분리

다음 세 상태로 나눈다.

```text
governance_bootstrap_allowed
implementation_setup_allowed
implementation_attempt_entry_allowed
```

`implementation_setup_allowed`에서는 compatibility tooling code와 tests만 작성·검토할 수 있다.

금지:

- Phase 0 census
- package/exporter execution evidence
- candidate policy 생성
- claim-bearing report
- live manifest mutation

tooling 구현과 implementation-result review가 끝난 후 attempt를 reserve하고 Phase 0을 시작한다.

어느 방식을 선택하든, ad hoc 외부 스크립트나 수동 절차를 Gate B authority로 사용해서는 안 된다.

**Blocking Reason:**

현재 계획의 절차만으로는 `implementation_entry_allowed=true`에 도달할 수 없다.

### Issue RTC-C5-2 — Owner-Bound Disposition Authority Records가 Durable Contract에 포함되지 않음

**Severity:** Critical

**Impact:**

roadmap과 계획은 Branch A exception이 owner-bound여야 한다고 명시한다.

현재 candidate policy/disposition은 다음 hash를 소비한다.

```text
plan_contract_approval_record_sha256
C-6 owner role record hash
```

그러나 durable bundle의 8개 role에는 다음 record가 포함되지 않는다.

- `plan_contract_approval_record.json`
- collision disposition owner record
- C-6 role assignment record
- Review 2 ratification record

durable bundle은 다음만 포함한다.

```text
policy
exclusion
disposition
candidate binding
package guard contract
implementation toolchain
toolchain freshness
pre-adoption machine result
```

owner record는 `owner_inputs` 경로에 있다고만 되어 있으며 다음이 고정되지 않았다.

- exact durable path
- tracked/not-ignored requirement
- immutable version
- bundle role
- live required manifest consumption
- clean-checkout presence
- replacement/supersession 규칙

따라서 clean checkout에서 다음 상황이 가능하다.

```text
durable disposition 존재
owner record content 부재
disposition 안에는 과거 owner-record hash만 존재
required gate가 owner record의 schema·identity·선택 내용을 재검증하지 못함
```

이는 roadmap의 다음 invalidation 조건과 충돌한다.

```text
owner record 또는 hash binding이 없음
→ exception fail-closed
```

또한 `RTC-RM-03-owner-record-missing` fixture를 production required route와 같은 방식으로 구현하기 어렵다. required route가 owner record를 직접 요구하지 않는다면 fixture만 owner record absence를 검사하고 실제 current gate는 검사하지 않는 이중 계약이 생긴다.

**Affected Scope:**

- plan contract approval
- C-6 role contract
- Phase 0B
- Change 2
- durable bundle
- live required-validation
- owner binding fixture

**Related Surface:**

- Authority Surface
- Sealed Artifact Surface
- Compatibility Surface

**Required Fix:**

owner/review authority record를 versioned durable contract에 포함해야 한다.

권장 durable bundle role 추가:

```text
plan_contract_approval
collision_owner_disposition
phase0_contract_review
```

최소 durable set:

```text
plan_contract_approval_record.json
current_collision_owner_disposition_record.json
phase0_disposition_contract_review_record.json
```

각 record는 다음을 가져야 한다.

- owner/reviewer identity
- role/eligibility
- timestamp
- selected decision
- target plan/policy/disposition hash
- input artifact hashes
- record self-hash 또는 외부 binding
- supersession status

candidate binding DAG는 다음처럼 유지할 수 있다.

```text
owner approval record
owner collision record
Review 2 record
policy
exclusion
disposition
→ external contract bundle manifest
```

live required manifest 또는 required unittest는 다음을 직접 검증해야 한다.

```text
owner record present
owner record tracked/not ignored
owner record hash matches
owner decision matches disposition
Review 2 PASS matches policy/exclusion
reviewer eligibility valid
```

durable promotion role count와 bundle ID 계산도 이에 맞게 수정해야 한다.

**Blocking Reason:**

현재 durable exception은 `owner-bound exception`이 아니라 `과거 owner hash를 문자열로 포함한 exception`으로 축소될 수 있다.

### Issue RTC-C5-3 — Final Canonical Closeout Evidence가 Disposable Local Evidence에만 존재함

**Severity:** Critical

**Impact:**

formal closeout은 다음 artifact를 요구한다.

```text
final_machine_report.json
independent_review_gate_report.json
owner_canonical_seal_gate_report.json
final_registry_runtime_compatibility_report.json
terminal_hash_seal.json
```

그러나 이 파일들은 모두 local attempt root의 `phase5/`에 남는다.

Evidence classification상 local attempt root는:

```text
supporting_generated
→ terminal sealing 이후 clean-checkout requirement 아님
```

tracked per-attempt durable surface에는 다음만 남는다.

```text
reservation_record.json
terminal_record.json
evidence_manifest.json
failure_summary.json
```

즉 terminal record와 evidence manifest가 final artifacts의 hash를 보존할 수는 있지만, 해당 artifact의 실제 bytes는 clean checkout에서 사라질 수 있다.

이 상태에서는 미래 auditor가 다음을 검증할 수 없다.

- independent review가 어떤 finding을 검토했는가
- reviewer eligibility가 실제로 무엇이었는가
- owner가 어떤 final machine report에 seal했는가
- final claim boundary가 무엇이었는가
- terminal hash seal이 어떤 artifact graph를 봉인했는가

남는 것은 검증할 원문 없이 존재하는 SHA-256뿐이다.

이는 다음과 같은 상태다.

```text
hash exists
referenced evidence bytes absent
canonical closeout content unverifiable
```

final claim-bearing evidence는 일반 supporting log와 동일하게 폐기 가능해서는 안 된다.

**Affected Scope:**

- Change 7
- Evidence Classes
- per-attempt durable records
- terminal transaction
- independent review
- owner seal
- final claim
- clean-checkout validation

**Related Surface:**

- Sealed Artifact Surface
- Authority Surface

**Required Fix:**

final governance packet을 tracked immutable per-attempt durable surface로 보존해야 한다.

권장 구조:

```text
Iris/_docs/round3/registry_runtime_compatibility/
  attempts/attempt-NNNN/
    reservation_record.json
    terminal_record.json
    evidence_manifest.json

    closeout/
      final_machine_report.json
      independent_review_gate_report.json
      owner_canonical_seal_gate_report.json
      final_registry_runtime_compatibility_report.json
      terminal_hash_seal.json
```

필요하다면 다음도 포함한다.

```text
post_adoption_current_route_result.json
live_gate_package_finalization_result.json
final_claim_scan_report.json
```

필수 ordering:

```text
final machine report
→ independent review
→ owner seal
→ final compatibility report
→ terminal hash seal
→ durable closeout packet commit
→ terminal record/event transaction
```

terminal event는 durable closeout packet commit을 직접 참조해야 한다.

clean-checkout validator는 다음을 요구해야 한다.

```text
durable_closeout_artifact_missing_count = 0
durable_closeout_hash_mismatch_count = 0
independent_review_content_available = true
owner_seal_content_available = true
terminal_seal_content_available = true
```

local phase5 copies는 provenance source가 될 수 있지만, canonical closeout authority는 tracked durable closeout packet이어야 한다.

**Blocking Reason:**

현재 계획으로는 `registry_runtime_compatibility_canonical_complete`의 근거가 terminal 이후 사라질 수 있다.

## 4. Non-Critical Issues

### RTC-I5-1 — Durable Bundle Lifecycle State의 Authority Surface가 불명확함

**Severity:** Important

계획은 다음 lifecycle을 정의한다.

```text
candidate
canonical_durable
package_guard_active_not_required_gate_adopted
live_required_gate_adopted
invalidated
superseded
```

그러나 `durable_bundle_lifecycle_report.json`은 local attempt evidence다.

다음 상태가 durable하게 어디에 기록되는지 명확하지 않다.

- invalidated
- superseded
- package_guard_active_not_required_gate_adopted

live manifest가 선택한 bundle은 `live_required_gate_adopted`를 간접적으로 나타낼 수 있지만, 비선택 bundle의 invalidation/supersession은 clean checkout에서 확인하기 어렵다.

**Recommended Fix:**

append-only durable bundle lifecycle event를 둔다.

```text
bundle_lifecycle_events.jsonl
```

또는 bundle별 immutable event record를 추가한다.

bundle directory 자체를 수정하지 않고 additive event로 상태를 관리해야 한다.

실제 repository diff나 command receipt는 아직 존재하지 않으므로 runtime compatibility 성공 여부는 판단하지 않았다.

content_reuse와 기존 bundle lifecycle state의 교차 의미론 미정의. 같은 content-addressed destination이 이미 존재하고 byte-exact일 때 content_reuse=true로 재사용하는데, 그 기존 bundle의 lifecycle state가 invalidated 또는 superseded인 경우의 처리가 미정의다. invalidation 사유가 attempt-국소적(예: 당시 toolchain drift)이었다면 새 attempt의 fresh probe로 동일 내용을 재정당화하는 것이 논리적으로 가능하나, invalidated → canonical_durable 전이가 허용되는지, 아니면 새 attempt가 별도 supersession record를 요구하는지 한 문장으로 고정할 것. 현 상태로도 오독 시 결과는 block(안전 방향)이므로 비차단.
