# 0. 종합 결과

## 0.1 공통 채택 항목

두 로드맵은 다음 사항에 실질적으로 합의한다.

- 문제의 본질은 Registry Authority 부재가 아니라 consumer별 identity semantics 차이다.
- `exact_runtime_identity`와 `consumer_comparison_identity`를 분리해야 한다.
- comparison identity는 collision 탐지 전용이며 runtime lookup, alias resolution, source authority를 대체하지 않는다.
- 현재 관찰된 collision은 `Base.LemonGrass` / `Base.Lemongrass`이다.
- 현재 수치인 `2105 entries`, `collision group 1`은 관찰값이며 실행 시 fresh preflight로 재파생해야 한다.
- owner disposition 없이 구현자가 collision을 alias 또는 intentional coexistence로 판정해서는 안 된다.
- Phase 0에서 Branch A/B/C를 결정한다.
- Branch A에서만 compatibility 구현을 계속한다.
- Branch B는 bounded source identity correction scope로 이관한다.
- Branch C는 owner disposition 부재로 fail-closed 차단한다.
- exception은 단순 코드 allowlist가 아니라 owner-bound·hash-bound policy여야 한다.
- bridge, chunk, package가 동일한 compatibility contract를 소비해야 한다.
- JSON property map으로 materialization하기 전에 duplicate와 collision을 탐지해야 한다.
- Windows 공식 inspection route는 object property map이 아닌 lossless record projection을 사용해야 한다.
- PowerShell 5.1 `ConvertFrom-Json`은 main rendered object의 row-key identity 검사에 사용하지 않는다.
- 최소 fixture 10종과 기존 exact-duplicate regression을 유지한다.
- 기존 stale bridge, monolith, predecessor reentry, forbidden-path, Lua syntax guard를 완화하지 않는다.
- required-validation adoption은 기존 container와 gate를 제거하지 않는 additive 방식이어야 한다.
- independent review와 owner seal은 서로 대체하지 않는다.
- 최대 claim은 `Registry Runtime Compatibility PASS`뿐이다.

## 0.2 비충돌 세부사항 채택

한쪽 안에만 구체적으로 제시되었지만 다른 안과 충돌하지 않는 다음 항목은 종합 로드맵에 포함한다.

# 1. Problem Statement

Iris Artifact Registry는 다음 current identity chain을 이미 current authority로 소유한다.

```text
current source
→ rendered artifact
→ Lua bridge export
→ runtime chunk manifest/chunks
→ isolated package projection
```

현재 문제는 authority 선정이 불명확하거나 current artifact가 누락된 것이 아니다.

문제는 Registry가 보존하는 exact key 집합을 consumer가 서로 다른 identity semantics로 읽을 수 있다는 점이다.

현재 관찰된 collision group은 다음과 같다.

```text
Base.LemonGrass
Base.Lemongrass
```

Lua table과 case-sensitive parser는 두 exact key를 별도 entry로 보존할 수 있다.

반면 Windows PowerShell 5.1의 `ConvertFrom-Json`은 두 property를 case-insensitive duplicate로 판정하여 main rendered object를 읽지 못한다.

따라서 하나의 current artifact가 consumer에 따라 다음처럼 다르게 해석될 수 있다.

```text
case-sensitive consumer
→ exact key 2개 보존

case-insensitive property-map consumer
→ parse failure
→ silent merge
→ overwrite
→ cardinality 감소 가능
```

이 상태에서는 다음 문제가 발생한다.

- current registry cardinality가 consumer별로 다르게 보고될 수 있다.
- exact key 집합이 Windows-side inspection에서 보존되지 않을 수 있다.
- 한 exact key의 payload가 다른 exact key의 payload를 덮어쓸 수 있다.
- bridge, chunk, package 검증이 통과해도 inspection route가 identity를 손실할 수 있다.
- 기존 exact-duplicate guard가 case-insensitive collision을 탐지하지 못한다.
- 기존 package guard가 stale bridge와 monolith는 차단하지만 comparison collision은 검사하지 않는다.
- owner disposition 없이 구현자가 collision을 alias 또는 intentional coexistence로 해석할 수 있다.
- `Registry Authority PASS`가 runtime consumer compatibility까지 포함한다고 오독될 수 있다.

따라서 최소한 다음 두 identity를 독립 계약으로 정의해야 한다.

```text
exact_runtime_identity
consumer_comparison_identity
```

## 1.1 exact_runtime_identity

Registry authority chain과 Lua runtime이 보존해야 하는 원래 key identity다.

공통적으로 합의된 성질은 다음과 같다.

- case-sensitive
- trimming 없음
- separator 변경 없음
- punctuation 변경 없음
- implicit normalization 없음
- aliasing 없음
- canonical/exception role과 무관하게 각 exact key를 별도 entry로 유지
- source/rendered/runtime/package에서 동일한 identity를 복원할 수 있어야 함

문자열 code-point 기준과 byte-exact 기준 중 어느 계약을 채택할지는 C-1에서 판정한다.

## 1.2 consumer_comparison_identity

case-insensitive consumer compatibility를 분석하기 위한 collision identity다.

```text
consumer_comparison_identity
= collision detection / compatibility analysis only

consumer_comparison_identity
!= runtime lookup key
!= source authority key
!= alias resolution key
!= source correction key
```

comparison algorithm은 다음 공통 제약을 만족해야 한다.

- deterministic
- locale-independent
- versioned
- trimming 없음
- punctuation normalization 없음
- separator normalization 없음
- module-name normalization 없음
- comparison 용도 외 사용 금지

구체적인 v1 algorithm은 C-2에서 판정한다.

## 1.3 필수 불변조건

각 필수 surface와 consumer는 다음을 만족해야 한다.

```text
전체 cardinality 보존
exact key 집합 보존
각 exact key와 payload 연결 보존
round-trip exact identity 복원
silent merge 금지
silent overwrite 금지
silent loss 금지
```

현재 보고된 `2105 entries`와 `collision group 1`은 독립 authority나 코드 상수가 아니다.

모든 count와 collision inventory는 실행 시점의 current surface에서 fresh하게 재파생한다.

# 4. Constraints

## 4.1 Authority preservation

Branch A에서는 다음을 변경하지 않는다.

- source authority
- exact key spelling
- rendered payload 의미
- rendered item text
- runtime payload 의미
- 두 collision member의 존재
- current authority chain
- predecessor/historical/staging 지위

다음 작업은 금지한다.

- key 삭제
- source rename
- alias writer 추가
- Registry Authority closure 재수행
- successor identity chain 재봉인
- predecessor authority 복구
- historical artifact current 승격

## 4.2 Responsibility preservation

- DVF Body Compiler에 runtime compatibility 책임을 추가하지 않는다.
- Lua renderer에 collision repair 책임을 추가하지 않는다.
- runtime에서 source를 재검증하지 않는다.
- runtime에서 key를 case-normalize하지 않는다.
- runtime에 JSON parser를 추가하지 않는다.
- Publish Boundary 문제를 포함하지 않는다.
- package publication이나 release readiness를 주장하지 않는다.

## 4.3 Identity preservation

- comparison identity는 exact identity를 대체하지 않는다.
- canonical role은 runtime lookup 우선순위가 아니다.
- compatibility exception은 alias가 아니다.
- payload-equivalent라도 exact key를 병합하지 않는다.
- identity를 보존하지 못하는 property-map consumer는 record-array projection으로 우회한다.
- materialization 전에 key collapse 가능성이 있는 parser는 canonical validation route로 사용하지 않는다.

## 4.4 Comparator constraints

`consumer_comparison_identity`는 다음 공통 제약을 갖는다.

- deterministic
- locale-independent
- versioned
- no trim
- no punctuation normalization
- no separator normalization
- no module-name normalization
- collision analysis 전용

구체 algorithm은 C-2 판정 전까지 구현하지 않는다.

## 4.5 Count and hash constraints

- `2105`를 성공 predicate 또는 코드 상수로 사용하지 않는다.
- `collision group 1`을 일반 validator 상수로 사용하지 않는다.
- source cardinality는 current source adapter에서 파생한다.

# Phase 3 — Windows Consumer Tooling

## Goal

PowerShell 5.1에서 main rendered object의 exact identity를 손실하지 않고 검사할 수 있는 공식 Windows inspection route를 제공한다.

## Entry Conditions

- C-4 canonical route 판정
- Phase 1 contract PASS
- common analyzer 사용 가능

## Primary Changes

### A. Main object inspection prohibition

PowerShell 5.1 `ConvertFrom-Json`을 다음 용도로 사용하지 않는다.

```text
main rendered object row-key identity 검사
exact key cardinality 측정
exact key-set 비교
collision group 검출
round-trip identity 검증
```

PowerShell 전체 사용을 금지하는 것은 아니다.

`ConvertFrom-Json`은 exact key가 property name이 아닌 record-array report 또는 sidecar를 읽는 데 사용할 수 있다.

### B. Canonical Windows route

C-4 판정으로 다음 후보 중 canonical route를 확정한다.

**후보 A**

```text
PowerShell wrapper
→ uv run python
→ duplicate-aware rendered reader
→ record-array projection
→ compatibility report
```

**후보 B**

```text
PowerShell wrapper
→ approved jq route
→ record-array projection
→ compatibility report
```

**후보 C**

```text
PowerShell wrapper
→ approved duplicate-aware reader
→ hash-bound record-array sidecar
→ compatibility report
```

어느 후보를 채택하더라도 다음은 금지한다.

```text
required dependency missing
→ ConvertFrom-Json main object fallback
```

dependency 부재 시 actionable error와 non-zero exit를 반환한다.

### C. Record-array projection

```json
[
  {
    "exact_key": "<exact-key-1>",
    "comparison_key": "<contract-derived>",
    "role": "canonical",
    "payload": {}
  },
  {
    "exact_key": "<exact-key-2>",
    "comparison_key": "<contract-derived>",
    "role": "compatibility_exception",
    "payload": {}
  }
]
```

metadata:

- projection schema version
- source path
- source hash
- policy hash
- owner record hash
- generated record count
- exact key-set hash
- payload-binding hash
- source order

### D. Round-trip restoration

PowerShell case-insensitive hashtable 안에서 round-trip을 수행하지 않는다.

```text
rendered object property-pair stream
→ record-array projection
→ exact-keyed serialized reconstruction
→ duplicate-aware reread
→ exact key/payload comparison
```

검증 대상:

- restored cardinality
- restored exact key-set
- contract가 order를 요구하는 경우 restored order
- exact key별 payload binding
- lost/merged/overwritten count

### E. Windows report

공식 report는 최소한 다음을 포함한다.

```text
source cardinality
rendered cardinality
runtime cardinality
package cardinality

exact distinct count
exact duplicate count

comparison collision group count
unauthorized collision count
exception-backed collision count

round-trip restored exact key count

merged key count
lost key count
overwritten key count

surface key-set mismatch count
surface payload mismatch count

policy hash validation
owner binding validation
artifact binding validation
```

## Expected Risks

- wrapper가 Python/jq stderr 또는 exit code를 숨김
- space/non-ASCII path invocation 실패
- Windows newline/encoding 차이로 hash mismatch
- sidecar가 authority로 오독됨
- adapter별 comparison algorithm drift
- wrapper 내부에서 main-object `ConvertFrom-Json` fallback 발생

## Expected Validation

- Windows PowerShell 5.1 invocation
- path-with-spaces fixture
- UTF-8 input/output fixture
- missing dependency fail-closed test
- forbidden main-object `ConvertFrom-Json` route scan
- adapter/report count parity
- sidecar cardinality preservation
- round-trip exact key restoration
- current collision positive inspection
- current full payload inspection
- source hash binding

## Expected Deliverables

Evidence:

## Exit Conditions

- main rendered object identity 검사에 `ConvertFrom-Json` 사용 0
- Windows projection cardinality loss 0

# 11. Rollback Strategy

## 11.1 Phase 0 이전

compatibility tooling mutation이 없으므로 roadmap 문서만 수정하거나 폐기할 수 있다.

## 11.2 Phase 0 Branch B 또는 C

구현을 시작하지 않는다.

- Branch B: bounded authority correction handoff만 보존
- Branch C: blocked owner disposition report만 보존

source/rendered/runtime/package를 임시 수정해 우회하지 않는다.

## 11.3 Adoption 이전

신규 tooling에 결함이 있으면 implementation diff를 revert하거나 격리할 수 있다.

다음 evidence는 삭제하지 않는다.

- failed fixture result
- failed current regression
- failed package probe
- review finding
- owner disposition
- invalidated policy record

새 실행은 새 attempt identity 또는 새 evidence path를 사용한다.

## 11.4 Adoption 이후

live required-validation entry나 package guard를 조용히 제거하거나 advisory로 낮추지 않는다.

rollback에는 다음이 필요하다.

- explicit rollback reason
- affected adoption entry
- before/after hash
- preserved prior PASS/FAIL evidence
- package guard 상태
- independent review
- owner approval
- current-route rerun

변경 이력은 supersession 또는 동등한 append-only 방식으로 보존한다.

## 11.5 Exception invalidation 이후

artifact drift 또는 payload divergence로 exception이 무효화되면 자동 재사용하지 않는다.

```text
exception invalidated
→ bridge/package/adopted route blocked
→ new owner disposition required
```

source correction이 필요하면 Branch B successor scope로 이관한다.
