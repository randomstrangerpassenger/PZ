# 문제화 템플릿 — 로드맵 작성 입력

## 사용 목적과 작성 규칙

이 템플릿으로 작성한 문제 문서를 웹의 ChatGPT와 Claude에게 각각 전달한다. 아래 공통 문서는 기존 작성 지침에 따라 활용된다는 전제이며, 이 템플릿은 읽기 의무나 순서를 다시 정하지 않는다. 저장소 코드, 문제별 원본 로그·감사 보고서, 별도 모듈 문서, 이전 대화까지 열람할 수 있다고 가정하지 않는다.

공통 문서의 접근 범위는 다음과 같다. 접근 가능 여부가 모든 문서의 선행 열람을 뜻하지는 않는다.

- `Philosophy.md`, `DECISIONS.md`, `ARCHITECTURE.md`, `ROADMAP.md`
- `ROADMAP_TEMPLATE.md`, `REVIEW_TEMPLATE.md`, `PLAN_TEMPLATE.md`, `EXECUTION_CONTRACT.md`
- `Pulse 생태계 각 모듈별 기능.txt`, `Pulse 생태계 공개 전략.txt`

공통 문서는 생태계의 기준과 맥락을 제공하고, 문제 문서는 그 문서들만으로 알 수 없는 해당 문제의 사실·요구·제약을 제공한다. 문제 작성자는 필요한 정보를 확인하여 본문에 정리한다. 로드맵 작성자는 이 입력으로 문제 해결에 필요한 사항을 설계한다. 이후 Codex가 실제 파일·심볼·명령을 확인하여 실행 계획을 구체화한다.

문제 문서는 해결해야 할 결과와 실제로 필요한 경계를 명확히 하고, 해결 수단은 기본적으로 열어 둔다. 접근 방식, 작업 분해, 단계 수와 순서, 중간 산출물, 검증 설계는 기존 계약이나 명시적 요구로 고정된 부분 외에는 로드맵 작성자가 선택한다. 이 템플릿의 예시와 질문은 새로운 실행 의무나 검토 통과 조건이 아니다.

- 문제를 구현·수정·조사·통합·검증 중 하나로 제한하지 않는다. 원인 규명이 목표라면 그에 맞는 산출물과 완료 조건을 작성한다.
- 필수 정보는 문제 정의, 필요한 배경과 현재 상태, 목표, 범위, 완료 조건이다. 관련 없는 항목·표·예시는 삭제하거나 합칠 수 있다. 설계 선택지를 미리 열거할 필요는 없다.
- 사실, 요구사항, 가설, 제안을 구분한다. 확인하지 못한 내용은 `미확인`으로 표시하고 확인 경로를 적는다. 미확인을 없음·0·완료로 취급하지 않는다.
- 이 템플릿은 기존 작성 지침이나 공통 문서의 권위·적용 범위를 변경하지 않는다.
- 공통 문서에서 이미 보장하는 요구는 반복하지 않는다. 이번 문제의 범위·순서·정확성·검증·주장에 미치는 구체적인 영향이 필요할 때만 적는다.
- 공통 문서 밖의 정보가 필요하면 핵심 내용을 문제 본문에 설명한다. 접근할 수 없는 문서명·경로·hash만으로 필요한 설명을 대신하지 않는다. 공통 문서에 다른 파일의 링크가 있다고 해서 그 파일도 제공된 것으로 간주하지 않는다.
- 세부 설계가 아직 없다는 이유로 모든 항목을 추정해서 채우지 않는다. 결과를 고정하는 데 필요한 정보와 로드맵이 설계할 사항을 구분한다. 작성자의 선호나 예시를 필수 조건으로 바꾸지 않는다.

## 3. 필요한 배경과 현재 상태

### 용어와 구성 요소

기존 지침에 따라 관련 공통 문서를 활용하는 작성자에게도 추가 설명이 필요한 문제별 용어와 역할을 적는다. 공통 문서에 정의된 기본 모듈 설명은 반복하지 않는다. 문제별 내부 약어·단계명·상태값은 이름만 나열하지 않는다.

| 용어 또는 구성 요소 | 이번 문제에서의 의미와 역할 | 다른 요소와의 관계 또는 책임 경계 |
|---|---|---|
| <모듈, owner, 단계, 데이터, 상태값 등> | <무엇을 의미하고 무엇을 담당하는지> | <어디에서 받아 무엇을 넘기며, 무엇은 담당하지 않는지> |

필요하다면 이번 문제에 관련된 입력 → 처리 → 출력의 현재 흐름을 짧게 설명한다. 전체 생태계 설명이나 구현 전문을 넣을 필요는 없다.

### 현재 확보된 것과 남은 차이

| 항목 | 현재 상태와 확인 내용 | 충족하지 못한 요구 또는 확인 한계 |
|---|---|---|
| <기능, 데이터, 계약, 검증 등> | <구현됨 / 검증됨 / 일부만 확보됨 / 미확인을 구체적으로 설명> | <로드맵에서 다뤄야 하는 차이> |

관찰이나 검증 결과가 판단에 중요하면 조건·대상 범위·결과·한계를 본문에 요약한다. 로그나 보고서 경로만 적지 않는다. 원인 추정은 확인된 현상과 구분한다.

공통 문서와 상충하거나 서로 맞지 않는 사실·규칙이 있다면 충돌 내용을 적는다. 대화에만 존재하는 핵심 결정도 이 문서에 포함한다. 문제별 원본 근거는 문제 작성자가 확인하며, 웹의 로드맵 작성자에게 미제공 근거 파일의 재감사를 요구하지 않는다. 공통 문서에 이미 충분히 설명된 현재 상태는 해당 절을 참조하고, 추가 정보만 적는다.

## 4. 목표

해결 후 관찰할 수 있어야 하는 상태를 작성한다. 구현 수단과 작업 목록은 로드맵에 맡긴다.

- 반드시 달성해야 하는 결과:
- 선택적으로 달성할 수 있는 개선: 해당할 때만 작성. 필수 범위에 자동 편입하지 않는다.
- 목표 간 충돌 시 우선순위: 기존 authority 또는 사용자 요구로 정해진 경우에만 명시한다. 미정이면 §8의 미확인 사항으로 남길 수 있다.

수치 목표가 이미 정해졌다면 측정 대상, 기준값, 수치의 의미와 설정 이유를 함께 적는다. 미정인 목표값을 임의로 고정하지 말고, 로드맵에서 기준을 수립해야 하는지 명시한다.

목표를 달성할 유일한 방법이 입증되거나 요구된 경우가 아니라면 특정 기술, 도구, 구조 또는 단계 구성을 목표에 포함하지 않는다.

## 5. 대상, 책임 경계 및 범위 밖

### 포함 대상

- 대상 동작, 데이터, 사용자 흐름 또는 계약:
- 책임을 가진 모듈 또는 authority:
- 관련 인터페이스·외부 의존성과 영향 경계:
- 대상 범위의 식별 방법: 전체 집합·표본·버전·환경 등이 정확성에 영향을 줄 때 작성.

증상이 나타난 위치만으로 변경 책임을 확정하지 않는다. 소유자가 미정이면 결정 또는 확인 사항으로 남긴다.

### 범위 밖

이번 문제와 혼동하기 쉬우나 포함하지 않는 작업을 적는다. 제외 사유가 선행 작업·후속 단계·별도 owner 책임과 관련되면 함께 적는다. 문제에 열거되지 않은 중간 작업이라는 이유만으로 범위 밖으로 취급하지 않는다. 목표 달성에 필요한 작업은 명시된 경계 안에서 로드맵 작성자가 도출할 수 있다.

### 작업 조건

후속 계획·실행에서 사용 가능한 환경, 데이터, 도구, 검증 수단, 시간 또는 자원 제한 중 전략에 영향을 주는 조건만 본문에 설명한다. 웹 작성자가 직접 실행할 수 있다는 의미로 쓰지 않는다. 알고 있지 않은 제한을 만들지 않는다.

## 6. 선행 조건과 의존 관계 — 해당 시

| 필요한 선행 상태 또는 입력 | 현재 충족 여부와 충족 판정 기준 | 필요한 시점 | 미충족 시 영향 |
|---|---|---|---|
| <다른 owner 결과, 계약 확정, 환경 등> | <현재 상태와 수용에 필요한 결과를 본문에 설명> | <특정 작업 전 / 통합 전 / 완료 판정 전 등> | <가능한 조사·작업과 진행할 수 없는 작업> |

- 계약 또는 실제 입력·출력 관계로 정해진 의존성:
- 순차·병렬 구성에 영향을 주는 알려진 조건:
- 통합 또는 후속 단계가 소비할 입력:

의존 관계 자체와 그것을 처리하는 단계 구성을 구분한다. 확정된 의존성이 허용하는 범위에서 작업의 묶음, 순서, 병렬성은 로드맵 작성자가 정한다. 아직 충족되지 않은 선행 상태를 완료된 것으로 가정하지 않는다.

## 7. 필수 불변식과 금지 사항 — 해당 시

해결 방식이 달라도 유지해야 하는 조건을 적는다. 보안, 호환성, identity, ownership, 데이터 보존, 의미 보존 등 이번 문제에 실제로 적용되는 항목만 포함한다.

조건을 필수로 둘 때는 적용 authority, 명시적 사용자 요구 또는 피할 수 없는 기술적 이유를 밝힌다. 선호하는 구현법은 이 절에 넣지 않고, 필요하면 §8의 참고 아이디어로 남긴다.

| 유지할 조건 또는 금지 행동 | 적용 이유 | 이번 문제에서의 구체적인 영향 |
|---|---|---|
| <문제별 조건 또는 공통 규칙의 구체적 적용> | <공통 문서의 해당 절 / 문제별 요구와 이유> | <어떤 설계·작업·검증을 제약하는지> |

공통 문서의 일반 규칙을 빠짐없이 복사하는 절로 사용하지 않는다. 공통 문서에 없는 문제별 계약은 “기존 계약과 동일”만으로 대신하지 말고 필요한 내용을 적는다. 특정 문제의 테스트 방식, 감사 절차, handoff gate를 모든 문제의 공통 규칙으로 옮기지 않는다.

## 8. 참고 아이디어와 불확실성 — 해당 시

### 참고 아이디어

아이디어를 제공할 필요가 없다면 이 부분을 생략한다.

- 참고할 접근 또는 후보:
- 참고할 만한 이유와 아직 확인하지 못한 점:

이 목록은 허용된 해법의 범위가 아니다. 로드맵 작성자는 후보를 채택·수정·배제하거나 다른 접근을 제안할 수 있다. 모든 후보를 비교하거나 각각의 미채택 사유를 작성할 의무는 없다. 확정된 결정은 공통 문서나 §4~7에서 구분하며 참고 아이디어로 위장하지 않는다.

### 미확인 사항

| 질문 또는 가설 | 판단에 미치는 영향 | 알려진 단서 또는 제약 |
|---|---|---|
| <모르는 것 또는 원인 가설> | <어떤 판단이 달라질 수 있는지> | <관찰 내용, 사용 가능한 확인 수단, 확정된 선행 조건 등> |

확인 방법이나 조사 순서를 문제 작성자가 미리 설계할 필요는 없다. 로드맵 작성자는 불확실성의 영향에 맞게 조사·분기·가정의 명시 등 적절한 처리 방식을 선택한다.

문제의 원인 해석이나 제안된 접근을 그대로 받아들일 필요는 없다. 다른 해석이 더 타당하다면 그 이유와 목표·범위에 미치는 영향을 설명할 수 있다. 확정 요구나 권위 경계의 변경이 필요하다면 승인된 변경인 것처럼 처리하지 말고 별도 제안으로 구분한다.

## 9. 완료 조건과 필요한 증거

문제의 목표가 충족됐는지 판정하는 결과 기준을 작성한다. 어떤 관찰 결과가 필요한지와, 그 결과를 어떻게 검증할지를 구분한다. 기존 계약이 정하지 않은 검증 수단은 로드맵에서 설계할 수 있다. 완료 조건은 현재 상태에 대한 PASS 주장이나 실행 승인으로 읽지 않는다.

| 완료 조건 | 관찰 또는 검증 대상 | 필요한 결과 또는 이미 확정된 증거 요건 | 알려진 한계 |
|---|---|---|---|
| C1. <달성해야 하는 결과> | <어떤 입력·범위에서 확인하는지> | <무엇을 검증하고 어떤 결과여야 하는지> | <미확인 / 검증 불가 / 해당 없음> |

- 필수 산출물과 후속 소비자: 기존 계약이나 명시적 요구가 있을 때 작성한다. 역할, 포함해야 할 정보, 수용 조건을 설명한다. 공통 문서에 없는 형식·schema가 설계를 제약한다면 필요한 구조와 규칙을 본문에 명시한다. 그 외 중간 산출물과 표현 형식은 미리 고정하지 않는다.
- 통과 전 생성·노출·변경하면 안 되는 산출물 또는 상태: 해당할 때만 작성.
- 완료의 적용 범위와 후속 단계에 허용되는 주장:
- 별도 검증 없이는 주장할 수 없는 후속 상태: 이번 문제와 실제로 혼동될 때만 작성.

작업 목록을 결과 기준으로 대신하지 않는다. 조사 문제에서는 근거 있는 원인 구분이나 의사결정 자료가 완료 결과일 수 있다.

반복 실행·비교기·finalizer가 문제별 필수 gate이고 공통 문서만으로 해석할 수 없다면 각각의 역할, 실행 순서 제약과 통과 조건을 본문에 설명한다. 이름이나 “canonical 검증”이라는 표현만으로 대신하지 않는다. 정확한 파일·심볼·명령은 이후 Codex가 계획에서 확인할 수 있지만, 로드맵의 방향을 결정하는 조건은 미루지 않는다. 공통 문서에서 이미 보장하는 검증 의무를 복제하거나 필수가 아닌 세부 절차를 형식적으로 추가하지 않는다.

## 10. 입력 전달 전 확인

문제 작성자는 기존 지침에 따라 공통 문서를 활용하되 저장소와 문제별 원본 자료, 이전 대화는 모르는 새 세션을 기준으로 다음을 확인한다.

- 공통 문서에 없는 문제별 용어와 구성 요소의 역할이 설명되어 있는가?
- 현재 확인된 상태, 남은 작업, 미확인 사항이 구분되는가?
- 필수 목표와 선택적 개선, 고정된 경계와 설계 여지가 구분되는가?
- 미제공 문서·로그·코드·이전 대화에 의존하지 않고 필요한 규칙과 상태를 알 수 있는가?
- 공통 문서와 문제 본문을 합쳐 산출물의 의미와 완료 판정 기준을 이해할 수 있는가?
- 실제 파일·명령을 몰라도 전략, 단계, 의존성, 검증 방향을 설계할 수 있는가?
- 공통 규칙을 불필요하게 복제하지 않으면서, `ROADMAP_TEMPLATE.md`를 상세히 작성할 문제별 정보가 있는가?
- 선호하는 해법·작업 순서·검증 방법을 근거 없이 필수 조건으로 고정하지 않았는가?

목표·필수 경계·완료의 의미 자체가 미정이라면 문제 작성 단계에서 가능한 만큼 명확히 한다. 본질적으로 미정인 내용은 숨기지 말고, 작성 가능한 조사 로드맵과 아직 확정할 수 없는 실행 방향을 구분한다. 제공되지 않은 원문이나 추가 첨부를 읽으면 된다는 방식으로 정보 공백을 남기지 않는다.

종합자에게도 같은 버전의 공통 문서·문제 문서와 두 로드맵을 전달한다. 서로 다른 접근이나 단계 구성을 그 자체로 결함으로 보지 않고 목표·제약·완료 조건에 비추어 비교한다. 제안을 모두 합쳐 범위를 늘리거나, 한 작성자의 가정을 확인된 사실로 바꾸지 않는다. 최종 로드맵에는 채택한 접근, 중요한 차이의 해소 근거, 남은 미확인 사항을 보존한다.
