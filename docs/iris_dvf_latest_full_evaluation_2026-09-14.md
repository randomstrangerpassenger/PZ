## 잘된 부분

일반 음식의 “먹을 수 있다 / 요리 재료로 쓸 수 있다”, 소독약의 “천, 솜, 상처를 소독”, 연료·수납·차량 교체 부품의 짧은 설명은 자신의 역할을 대체로 충족한다. 영양·성능·모든 부작용을 추가해야 한다고 평가하지 않았다.

천·데님·가죽 회수의 차이, 무전 송신과 방송 청취, 모닥불 도구·텐트·매트리스 제작, 도구와 재료의 여러 독립 용도는 이전보다 명확하다. 천 의류 Compact에서 시트 로프를 개별 열거하지 않고 Expanded에 보존한 것은 적절하다. 전자 회로 부속·삽·렌치 등은 Compact 개요와 Expanded 구체 용도의 깊이가 실제로 구분된다.

총기 부착물의 반동·사거리 등은 사용 목적에 해당하므로 효과를 남기는 것이 타당하다. 학습·수리 대상 목록은 내용이 길다는 이유로 결함으로 보지 않았다. 예컨대 접착 테이프의 `target_groups`에는 차량 부품·악기·스포츠 용품·원예 도구·창·도끼·칼날 도구·둔기와 도구의 8개 disclosure 범주가 실제로 있다. 직렬화된 전체 목록을 펼친 텍스트의 길이와 메뉴 정보 구조를 혼동하지 않았다.

## 확인된 교정 사항

### 1. 약초 찜질제는 적용 부위만 있고 치료 목적이 없다 — 3 ID

세 찜질제가 모두 다음 문장이다.

> 다친 부위에 바르는 약초 찜질제로 쓸 수 있다.

영어도 `It can be applied to an injured body part as an herbal poultice.`로 동일하다. 플레이어에게 어떤 부상을 위해 어느 찜질제를 쓰는지 알려주지 못한다. 이는 모든 효과를 설명하라는 요구가 아니라 **효과 자체가 사용 목적**인 경우다. 기준 1·3·5에 미달한다.

로컬 Lua의 `ISComfreyCataplasm`, `ISPlantainCataplasm`, `ISGarlicCataplasm`은 각각 다른 body-part factor를 설정한다. 설치 게임의 `BodyPart.class` 소비 경로를 추가로 판독했다.

- Comfrey: 골절 회복 시간 감소에 관여한다.
- Plantain: 긁힘·베임·깊은 상처의 회복 시간 감소에 관여한다.
- Wild garlic: 상처 감염 수준 감소에 관여한다.

이 정도의 목적 차이는 공개해야 한다. 배율·효과 지속 계산·조건 검사의 전부를 문장에 옮길 필요는 없다. 원료 약초에는 “해당 찜질제를 만드는 재료”라는 역할을 유지하고, 원료가 직접 치료하는 것처럼 효과를 상속하면 안 된다.

공통 원인: `description_composition_families.py:136` 부근의 `apply_poultice` 개요가 효과 관계를 사용하지 않는 단일 문장으로 끝난다. 해결은 적용 행동과 치료 목적의 공통 관계 연결이어야 한다.

### 2. 시계에 시간 확인 용도가 빠져 있다 — 16 ID, 특히 Classic 8 ID

Classic 손목시계 8종은 양쪽 모두 “왼쪽이나 오른쪽 손목에 골라 찰 수 있다.”뿐이다. 알람이 없는 것은 맞지만, 시간 확인까지 없는 것으로 처리해서는 안 된다. 나머지 디지털·알람 시계 8종도 알람과 분해 등을 설명하면서 시간 확인은 설명하지 않는다. 기준 1·4·9에 관한 누락이다.

설치 게임 `zombie.ui.Clock`의 `resize()`는 착용품과 소지품에서 AlarmClock/AlarmClockClothing을 찾으면 시계를 표시한다. `Digital` 태그는 digital 플래그에 따로 반영한다. `renderDisplay()`의 시간 숫자 출력과 `timeDigits()`의 GameTime 사용도 확인했다. 따라서 Classic 여부와 시간 확인 목적을 분리할 근거가 있다.

공개 목적은 “시간을 확인할 수 있다” 수준으로 충분하다. 디지털 시계의 날짜·온도 등까지 이번 지적을 이유로 자동 확장할 필요는 없다. 필요 조건은 실제 소지·착용 경로에 맞춰 설명한다. 모든 가방 내부 검색까지 된다고 주장하지 않는다.

### 3. 고장 난 낚싯대의 수리 관계가 일반 제작 재료로 바뀌었다 — 1 ID

`Base.FishingRodBreak`의 두 깊이는 “무기로 쓸 수 있다. 낚시 장비를 만들 때 재료로 쓸 수 있다.”이다. 실제 레시피는 `Fix Fishing Rod`이며 고장 난 낚싯대를 받아 정상 낚싯대로 돌려준다. `scripts/recipes.txt:1168`과 `1180`, 최종 JSON의 두 `use_relations` 결과에서도 확인된다.

현재 문장은 플레이어가 “고쳐서 다시 낚시할 수 있는 물건”을 알아보지 못하게 한다. 수리·복원되는 대상과 새 장비의 소모 재료를 구분해야 한다. 무기 용도는 독립적으로 남겨야 한다. 기준 1·4·5에 미달한다.

수량과 수리 레시피 전체는 필요 없다. 예컨대 “낚싯줄 등을 보충해 낚싯대로 고쳐 쓸 수 있다”처럼 실제 수리 관계가 이해되는 설명이 목표다. 예시 문구의 도구·재료 범위는 기존 확정 관계로 조정해야 한다.

### 4. 음료와 조리 바탕을 일괄 ‘요리를 만든다’로 설명한다 — 음료 관련 18 ID, 전체 검토 후보 65 ID

유리잔·와인잔·플라스틱 컵의 Expanded, 음료와 물 든 머그 등의 문장에 “재료를 더해 요리를 만들 수 있다 / Ingredients can be added to prepare food”가 공통으로 나타난다. `evolvedrecipes.txt`에는 음료 만들기, 컵에 맥주 붓기, 와인잔에 와인 붓기, 뜨거운 음료 만들기가 구별되어 있다. 음료 목적을 food라는 일반어로 덮는 것은 부정확하다.

또한 그릇의 Expanded는 Compact의 요리 개요를 다시 일반화해 말한다. 같은 자료에는 샐러드를 만드는 바탕이라는 구체성이 있다. 냄비의 수프·스튜, 빵의 샌드위치 바탕처럼 **용기·바탕·추가 재료·완성 음식**의 차이를 설명 구조가 활용하지 못하는 곳이 있다.

이 공통 문형이 있는 65 ID 전부가 결함이라는 뜻은 아니다. 이미 음식의 정체가 명확한 완성 요리는 간결한 설명이 충분할 수 있다. 18개 음료 관련 항목과 용기·바탕 역할을 우선 구분해야 한다. 개별 요리법을 독립 용도로 모두 늘어놓으라는 요구도 아니다. 기준 1·4·5·6·7에 따라 의미 있는 목적 수준에서 구분해야 한다.

공통 원인: `description_composition_results.py:69`, `description_composition_uses.py:1493` 부근의 일반 문형. 결과의 음료/음식 분야와 현재 투입 역할을 반영하고, Expanded에서 필요한 목적을 구체화해야 한다.

### 5. 좁은 제작 관계도 Expanded에서 넓은 분류로만 남는다 — 확인 사례 2 ID

- 쓰레기봉투: “건축 재료로 쓸 수 있다.”로 끝나므로 빗물받이 제작 활용이 보이지 않는다. `ISBuildMenu.onCreateBarrel`은 RainCollectorBarrel을 만들며 Garbagebag을 재료로 요구한다(`ISBuildMenu.lua:1390` 부근).
- 문손잡이: “목공과 건축 재료로 쓸 수 있다.”로 끝난다. 같은 코드의 문·양문 제작에 Doorknob이 연결된다(`1664`, `1678` 부근).

판자처럼 실제 활용 분야가 넓은 재료에 “목공·건축”을 쓰는 것까지 금지할 이유는 없다. 하지만 좁고 유용한 제작 대상이 확인된 항목의 Expanded까지 같은 상위 분류로 덮으면 추가 정보를 주지 못한다. 기준 5·7의 문제다. 현재 확인한 두 사례와 같은 관계를 가진 전체 적용 범위를 다시 점검해야 한다.

### 6. 복합 도구 Compact는 아직 기능 명사 목록에 가깝다 — 7 ID

톱의 현재 Compact:

> 음식, 목재 손질과 장비 제작, 개조, 건축물 해체에 쓸 수 있다.

영어는 `It can be used for food and wood preparation or equipment making and modification, or dismantling structures.`이다. 사냥용 칼·부엌칼·마체테·돌칼·고기용 식칼·정원용 톱도 같은 계열이다.

활용 분야가 부분적으로 보이지만, “장비 제작·개조”는 무엇을 위한 장비인지 지우고 영어 병렬도 부자연스럽다. 단순히 글자 수를 줄여 해결할 문제가 아니다. 확인된 제작 목적을 의미 있게 묶고, 첫 접근에서 유용하지 않은 세부 활용은 Expanded에 보존하는 편이 기준 5·7·8에 맞는다. 모든 도구에 고정 순위를 부여하거나 하나의 대표 용도로 축소해서는 안 된다.

공통 규칙 자체도 재검토가 필요하다. `_compact_purposes`의 직물·미용 두 후처리는 제거됐지만, 남은 복합 families와 cutting 선택 조건에도 `activity/function` 적합성 **또는** `role in {'tool', 'attachment'}` 같은 폭넓은 인정 조건이 남아 있다(`description_composition_results.py:502–519` 부근). 특정 용도 조합을 충족하면 완성된 복합 문장으로 바꾸는 방식도 남아 있다. 목적 분야별로 합성하고 무관한 활용은 유지하는 방식으로 바꿔야 한다. 현재 실제로 모든 추가 용도가 소실됐다고 단정하지는 않으며, 역할만으로 목적 범주를 인정하는 규칙 위험과 현재의 거친 문면을 구분한다.

### 7. 영어 결과명 삽입과 병렬의 잔여 결함 — 확인 사례 4 ID 이상

빈 맥주병·위스키병·와인병 2종은 `It can be broken to obtain Smashed Bottle.`이다. 단수 가산 결과에 관사가 없고 표시명 대문자가 문장에 그대로 들어갔다. `a smashed bottle`처럼 문장 속 명사구가 되어야 한다. 이는 개별 아이템 예외가 아니라 결과명 렌더링 공통 규칙의 적용 범위 문제다.

세척제 영어의 `washing the body and clothing and equipment with water`도 불필요한 and 반복이 남아 있다. 이런 문법·병렬 문제를 “영어 핵심 정보가 맞는다”는 이유로 통과시킬 수는 없다. 반대로 게임 자체의 영문 표시명과 한국어 번역이 다른 사례를 현실 지식만으로 임의 정정하지는 않았다.

## 확인된 경계와 추가 조사 사항

### 로프의 하강 용도 — 2 ID

Rope/SheetRope가 두 깊이에서 “설치해 위층으로 올라가는 데 사용할 수 있다”로만 설명된다. 설치 경로는 두 타입을 모두 받고, `ISClimbSheetRopeAction`에는 상승과 하강 분기가 있다. 네이티브 `ClimbThroughWindowState`도 하강 가능성을 검사한다. 창문 통과에서 하강 행동까지의 연결과 현재 근거 참조 연결을 추가 확인해야 한다. 위층 이동만을 목적처럼 제한한 설명을 그대로 최종 통과시키기보다 탈출·층간 이동 목적을 검토해야 한다. 모든 로프 설치 지점과 실패 조건을 문장에 열거할 필요는 없다.

### 단조의 현재 서바이벌 도달 가능성 — ‘단조’ 문형 16 ID

현재 데이터에는 단조 레시피와 필요 시설이 있지만, 설치본과 동일한 `ISBlacksmithMenu.lua:41` 부근에서는 `disableFurnaceAnvil = true`로 화로·모루 제작 메뉴가 비활성화돼 있다. 이는 “레시피 선언이 있으므로 현재 서바이벌에서 쓸 수 있다”는 판단을 다시 확인해야 하는 근거다.

이번에는 다른 월드 배치·시설 접근 경로까지 전수 조사하지 않았다. 따라서 단조 16 ID의 용도를 즉시 삭제하거나 불가능하다고 단정하지 않는다. 기존 근거와 실제 시설 도달 경로를 연결하는 조사가 필요하다. 이는 일반 문장 교정보다 사용 가능성 검증의 문제다.

### absent와 세부 정보

absent 129 ID 목록을 읽고 기록했지만, 각 항목의 모든 게임 기능이 없음을 증명한 것은 아니다. 구 ID·장식물·미지원 관계를 모두 누락 결함으로 계산하지 않았다. 음식 부작용·시계의 모든 표시 항목·발전기의 모든 위험·레시피 수량·실행 순서도 자동 추가 대상으로 삼지 않았다. 불쏘시개로 쓸 수 있는 장신구는 기존에 확인된 드럼 소비 경로가 있으므로 현실 상식만으로 제거하지 않았다.

## 평가 방법과 수정 방향

우선순위는 **목적 누락과 역할 오류 → Expanded의 필요한 구체성 → Compact의 의미 있는 묶음 → 양 언어의 문장 마감**이다. 개별 ID별 완성 문장이나 해당 아이템의 전체 특징 조합을 겨냥한 보정으로 해결해서는 안 된다. 목적·역할·결과 관계에 기반한 공통 규칙을 수정하고, 해당 규칙의 실제 적용 범위를 다시 읽어야 한다.

이번 작업은 읽기·근거 대조·평가 자료 생성이며 제품 코드나 설명을 수정하지 않았다. 따라서 제품 테스트를 다시 돌려 문장 품질 근거로 삼지 않았다. 검토 목록과 최종 JSON을 대조한 `uv run --project ./Iris/tooling python .tmp/dvf_full_review/audit.py`는 종료 코드 0이다. 앞선 테스트 통과는 위 결함을 해소하지 않는다.
