# Iris DVF 전체 아이템의 플레이어 관점 용도 설명 전환

## 1. 문제명과 입력 기준

- 문제명: 전체 2,105개 아이템의 DVF를 행동·관리 설명에서 플레이어 관점의 용도 설명으로 전환
- 입력 문서 버전 / 기준일: v1 / 2026-09-11
- 대상: Iris 3계층 DVF의 사실 해석, 의미 블록, 설명 조합, 품질 판단 및 기존 Tooltip/Menu 공급에 필요한 연결
- 기준 상태: 일부 기능군의 직접 교정 이후 실시한 전체 2,105개 조사 결과를 기준으로 한다. 교정된 파일을 전수 재생성했다는 사실과 전체 용도 선택 규칙을 교정했다는 사실을 구분한다. 이번 문제는 후자를 달성하지 못한 상태를 다룬다.

조사 입력은 `Iris/build/description/composition/descriptions.json`(SHA-256 `1DF567F8442BA93B76B4390FB8962D5FF98D7489223BE2A5EA2A7EDB0E424478`)과 `blocks.json`(`048D16806C5DC47254E47B35BBAFFA62C7F2C7DE0447CE92F88DCD701583ED52`)이다. 식별자는 조사 수치의 적용 대상을 뜻하며 새로운 봉인·증명 체계를 요구하지 않는다. 구현 시 현재 입력과의 차이는 확인해야 한다.

이 문서는 하나의 문제 입력이다. A·1·2·3을 각각 다시 문제화하거나 기존 단계 구성을 그대로 재실행하라는 요구가 아니다. 로드맵 작성자에게 저장소와 이전 대화가 제공되지 않는다는 전제로 필요한 상태와 경계를 아래에 설명한다.

## 2. 문제 정의

### 현재 상태와 기대 상태의 차이

현재 DVF는 아이템에 연결된 행동의 실행 조건, 관리 절차, 상태 변화와 내부 처리 정보를 문장화하는 경향이 강하다. 일부 사례에서는 구체적인 도구·결과물을 알고도 일반적인 역할 이름만 출력한다. 그 결과 플레이어가 읽어도 **이 아이템으로 무엇을 할 수 있는지**보다 **어떤 처리에 참여하며 실행에 어떤 조건이 필요한지**를 먼저 접한다.

사용자가 요구하는 용도는 아이템 자체 또는 내부 데이터의 시점이 아니라 **게임을 플레이하는 플레이어 시점의 활용**이다. 최종 기준은 “플레이어가 이 설명으로 아이템의 확인된 활용 목적·기능·결과를 이해하는가?”다. 능동태, `도구`·`재료` 역할의 정확성, 문장 수, 길이만으로 충족 여부를 판단할 수 없다.

- “전자 기기 분해에 쓰는 가공 대상이다”는 역할 기술이고, “분해해 수신기와 전자 부품을 얻을 수 있다”는 활용 설명이다.
- 양말의 세척·젖음·물 소비·이동 중단은 양말의 활용이 아닌 관리 절차다. 양말을 직물·시트 로프 재료, 연료·불쏘시개로 쓰는 것은 실제 활용이다.
- “알약을 복용할 수 있다”만으로는 복용 목적을 이해하기 어렵다. 그러나 미확인 효과를 만들어 채울 수는 없다.
- “통조림 따개로 개봉해 옥수수를 요리 재료로 쓸 수 있다”는 도구·내용물·용도가 근거로 연결된 경우에 적합한 방향이다. 예시를 개별 아이템의 확정 문안으로 고정하지 않는다.

기대의 근거는 Philosophy의 근거 기반 게임 내 위키와 이해 가능한 설명 원칙, 그리고 전체 2,105개에 플레이어 관점의 용도 중심 공통 규칙을 적용하라는 사용자 명시 요구다. 통조림·세척·발화만의 교정은 이 요구의 대체물이 아니다.

### 영향과 필요성

전수 조사에서는 한국어 1,599개에 결함이 보고됐다. 따라서 일부 문구의 미관 문제가 아니라 DVF의 핵심 전달 목적에 영향을 주는 문제다. 기존의 국소 교정과 많은 문장의 변경만으로 완료를 주장하면 다른 기능군의 동일 문제가 남는다는 실패가 이미 관찰됐다. 같은 선택·표현 경로를 사용하는 정규화된 신규 데이터에서도 반복될 위험이 있다. 이는 예상 위험이며 미래 모드에 대한 실측 결과는 아니다.

## 3. 필요한 배경과 현재 상태

### 구성 요소와 책임

| 구성 요소 | 역할과 현재 확보된 것 | 이번 문제와의 관계 |
|---|---|---|
| A: 근거·멀티 프로필 사실 | 하나의 primary_use로 축소하지 않고 여러 기능·재료·대상 역할, 조건과 결과를 보존 | 세척 대상/세척제, 불쏘시개/점화 도구 등이 상당 부분 구분돼 있다. 필요한 활용 근거·관계가 실제로 부족한 경우도 분리해야 한다. |
| 문제 1: 의미 블록 | 사실의 역할·맥락·조건 적용 범위·관계를 조합 입력으로 정리 | 내부 사실 보존은 필요하지만 블록 하나마다 공개 문장을 만들 의무는 아니다. |
| 문제 2: 설명 조합 | 같은 근거로 KO/EN compact와 expanded를 생성 | 공통 용도 선택·통합·명명·표현을 교정할 중심 영역이다. |
| 문제 3: 품질 판단 | 기존 문장과 근거의 대응, 표현 품질을 검토 | 과거 통과는 플레이어 관점의 용도 품질을 보장하지 않았다. 이번 의미에 맞는 판단이 필요하다. |
| B: Tooltip 공급·표시 | compact를 기존 Tooltip에 공급 | 이전 후보의 표시·연결은 사용자 인게임 통과. 새 설명의 품질 및 새 후보 표시까지 통과한 것은 아니다. |
| C: Menu 공급·구성 | expanded를 Browser/Wiki 메뉴에 공급 | 오프라인 구현 상태이며 실제 메뉴 품질은 미통과. 렌더러가 원문 의미를 고치는 책임을 맡지 않는다. |

흐름은 근거·사실 → 의미 블록 → 공개 용도 선택·문장 생성 → Tooltip/Menu다. 사실 자료는 29,202개, 대상 아이템은 2,105개이며 둘을 혼동하지 않는다. 내부 사실 보존과 공개 본문의 완전성은 별개의 개념이다.

### 전수 조사 결과와 한계

| 한국어 아이템 판정: 두 표면 통합 | 수 | 전체 대비 |
|---|---:|---:|
| 행동·관리 중심 | 1,027 | 48.79% |
| 용도와 불필요한 행동 설명 혼재 | 572 | 27.17% |
| 이번 기준의 결함 미확인 | 385 | 18.29% |
| 설명 부재 | 121 | 5.75% |
| 합계 | 2,105 | 100% |

결함 고유 아이템 1,599개(75.96%)는 두 표면 중 하나라도 결함이 있는 항목이다. compact 결함 1,057개는 모두 expanded에도 결함이 있고, expanded에만 결함인 항목은 542개다. 영어와 KO/EN 합집합도 조사상 각각 1,599개다. 네 표면 상태 8,420개를 대조했다는 조사 보고이며, 이 문서 작성자가 전수 판정을 독립 재실행한 결과는 아니다.

유형별 고유 아이템 수는 실행 절차·조건 1,575, 자체 관리 580, 과도한 추상화 497, 활용 정보 부족 241, 반복 166, compact 정보 밀도 137, 내부 표현 32, compact 독립 용도 누락 17, 역할 혼동 4, 적용 범위 불일치 1이다. 유형 간 중복이 있으므로 합산하지 않는다. 과거 교정의 “expanded 1,645개 변경”은 이 결함 수와 다른 지표다.

판정 보류는 0으로 보고됐지만 근거상 유보는 242개다. 241개는 활용 정보 부족을 확인했으나 미서술 효과·기능의 정확한 내용을 조사 입력으로 확정하지 않았다. 1개는 부서진 어망의 결과 표기 해석 한계다. 설명 부재 121개도 오류·정상 어느 쪽으로 자동 확정하지 않는다.

조사는 편집 판단이며 품질 합격 기준으로 고정된 authority가 아니다. 실제 양말 compact는 네 문장을 나열한 상태인데 조사에서는 결함 미확인으로 판정했다. 이는 사용자가 요구한 간결성과 정보 밀도 판단에 재확인이 필요함을 보여 준다. 따라서 385개를 무조건 통과시키거나 1,599개만 수정 대상으로 삼지 않는다. 조사상 누락 17개 역시 자동 재출력 목록이 아니라 공통 용도 요약에서 독립 활용이 실제 사라졌는지 판단할 근거다.

### 확인된 공통 결함과 일부 개선

최근 구현은 세척 대상·패치 대상·이름 변경 등의 명시적 목록을 비공개로 분리하고, 일부 개봉 결과와 도구를 구조화해 설명에 전달했다. 이는 보존할 개선이다. 그러나 그 규칙이 처리하지 않는 나머지 정보는 기존 expanded 경로에서 조건과 함께 문장화된다. 관리 기능을 단지 상세로 보내는 선택도 남아 있다.

사과에는 인벤토리 이전·이동 중단, 책에는 페이지·소지·운전·취소 조건, 망치에는 자기 수리 절차, 차량 부품에는 장착·탈거 절차에 비해 기능 설명 부족이 남는다. 새 점화 문장의 “해당 대상의 지원 상태”, 씨앗의 “선언된 내용물 수량”도 플레이어용 표현과 내부 근거 언어를 혼동한다.

기존의 모든 fact를 expanded 문장 참조로 보존하라는 검사 조건은 최근 교정에서 내부 보존과 공개 주장으로 분리됐다. 이 방향은 유지해야 한다. 무관한 사실 참조를 문장에 붙여 보존 검사만 만족시키는 방식은 허용하지 않는다.

## 4. 목표

- 전체 2,105개와 KO/EN compact·expanded에 일관된 플레이어 관점의 용도 판단·통합·표현 원칙이 적용된다. 이미 발견한 기능군에만 적용하고 나머지를 기존 나열 방식에 맡기지 않는다.
- 모든 확인된 독립 활용은 설명 체계에서 보존한다. compact는 그 활용을 이해 가능한 공통 용도로 요약하고 expanded는 대상·대안·결과의 차이를 확장한다. 짧게 만들기 위해 활용을 삭제하지 않는다.
- 일반 실행·관리 절차와 내부 처리 언어는 용도 설명을 대신하지 않는다. 필요한 한정과 구체적 이름·결과 관계는 보존한다.
- 상류 근거가 충분한데 표현이 부족한 경우와 근거 자체가 부족한 경우를 구분해 해결 또는 명시적으로 처리한다. 빈 문장이나 내부 용어로 불확실성을 덮지 않는다.
- 기존 A·1·2·3의 유효한 작업물을 활용하고 필요한 계약·판정도 일관되게 개정한다. B/C는 교정된 동일 자료를 소비한다.

결함 비율을 임의의 목표치까지 낮추거나 삭제로 0을 만드는 것이 목표가 아니다. 남는 미확정 항목은 근거와 처리 이유가 있어야 하며 해결 완료로 위장할 수 없다. 수치만으로 의미 품질을 대체하지 않는다.

## 5. 대상, 책임 경계 및 범위 밖

### 포함 대상

조사 기준의 exact item ID 2,105개 전체와 네 언어·표면 조합, 그 설명을 생성하는 기능·역할·조건·결과 유형 및 미처리 경로를 포함한다. 전체에 같은 판단 기준을 적용하라는 요구이지 2,105개의 수작업 문장을 만들라는 요구가 아니다. 코드·데이터·문서의 구체적인 수정 위치와 작업 분해는 로드맵 및 실행 계획에서 정한다.

공개 설명 선택, 상류의 필요한 역할·관계·명칭 전달, 실제 활용 정보 부족의 처리, 기존 검사 의미와 품질 판단, 교정 자료를 기존 B/C에 공급하는 데 필요한 변경을 포함한다. 소비자에서 일부 문장을 숨겨 생산자의 문제를 회피하지 않는다.

### 범위 밖

게임의 모든 미발견 사실을 새로 수집하는 사업, QG·정규화 어댑터 전면 재설계, L2 분류 재설계, Tooltip/Menu 전면 UI 개편, 다른 모듈 기능 변경, release·commit·push는 포함하지 않는다. 단 현재 대상의 활용 정보 부족을 해결하는 데 필요한 저장소 내 근거 확인은 범위 안이다. 항목이 예시에 없다는 이유로 제외하지 않는다.

### 작업 조건

기존 PZ 저장소에서 직접 작업하며 기존 dirty/deleted/untracked 변경을 보존한다. 새 worktree/clone을 만들지 않는다. 저장소 밖 파일은 채택 계획에 필수 입력으로 명시되지 않는 한 조사·수정하지 않는다. 향후 모드는 정규화 어댑터를 통해 바닐라와 유사한 입력 구조로 들어온다는 전제이며 임의 원시 입력을 가정해 범위를 키우지 않는다.

필요한 전체 결과 검토는 사용자 요구다. 이를 불필요한 전수 조사라며 표본으로 축소하지 않는다. 반대로 저장소 전체 Run A/B+comparator나 반복 재검증을 자동 추가하지 않는다. 계획에 명시된 필요한 검사만 가능한 마지막에 묶고, 계획에 없는 중간 테스트를 하지 않는다. 실행 중에는 주기적으로 상태를 확인하고 비정상 장기 실행을 중단할 수 있어야 한다.

## 6. 선행 조건과 의존 관계

| 입력 또는 상태 | 현재 상태 | 의존성 |
|---|---|---|
| 사실·블록·현재 설명 | 확보됨. 근거 부족 항목도 있음 | 실제 설명 교정 및 용도 보존 판단의 입력 |
| 전수 조사·항목별 이유 | 확보됨. 일부 판정 재확인 필요 | 범위와 원인 파악에 활용하되 기존 판정 자동 승계 금지 |
| 공개 선택과 표현의 공통 기준 | 사용자 목적은 확정, 적용 설계는 미완성 | 미처리 유형과 기존 fallback까지 일관되게 처리해야 함 |
| B/C 공급 | 기존 구현 존재 | 변경 모델이 필요한 경우 소비자와 일관성을 유지 |
| 사용자 실제 게임 관찰 | 이전 B 후보만 통과, 새 후보 미확인 | 새 Tooltip/Menu의 실제 표시·품질 최종 수락 전 필요 |

단계 수·순서·중간 산출물 형식은 고정하지 않는다. 동일 입력과 생산·실행 경계를 공유하는 확인은 결과를 공유할 수 있다.

## 7. 필수 불변식과 금지 사항

| 조건 | 근거와 구체적 영향 |
|---|---|
| 멀티 프로필·실제 독립 용도 보존 | 사용자 요구. primary_use 회귀나 어려운 활용의 일괄 삭제 금지 |
| 역할보다 플레이어의 활용 이해를 최종 기준으로 삼음 | 사용자 정정. 수동태 제거·역할명 교체·키워드 필터만으로 완료 불가 |
| 근거와 공개 표현을 구분 | 맞는 내부 사실과 역사 자료를 지우지 않음. 추측한 효과·결과를 추가하지 않음 |
| 필요한 한정은 유지 | 처리 대상 전체 제외 금지. 회수 재료 공급은 실제 활용일 수 있음. 확정/조건부 결과, 도구 대안, 재사용/소모 의미를 구분 |
| 구체적인 명칭과 관계 | 확인된 단일 개봉 도구는 통조림 따개로 명시. 복수 도구를 하나로 오축소하지 않음. 이름 접두사로 내용물 추측 금지. 결과의 모든 활용을 원래 아이템에 무제한 복사하지 않음 |
| 공통 생성 규칙으로 해결 | FullType별 완성 문장 패치·runtime 문장 교정으로 대체하지 않음. 입력 의미에 따른 유형별 표현은 가능 |
| Tooltip 책임 유지 | Alt 최대 4개 물리적 줄: L2 소분류 / DVF 요약 / 획득 장소 / 유효 L4 레시피·우클릭·자유 조리 후보 무작위. 폭 확장으로 여러 문장을 욱여넣는 것을 간결성 충족으로 보지 않음 |
| Menu와 Tooltip은 같은 사실의 다른 깊이 | Menu도 용도 중심. L4 상호작용 목록은 별도 책임이고 DVF에서 절차를 제외한다고 L4 후보를 삭제하지 않음 |
| 검증·문서의 절제 | 별도 seal/receipt/manifest/proof, validation-of-validation, 임시 검사기의 authority 승격 금지. 필요한 항목별 결과 기록은 허용. Gate마다 workspace 생성 금지, 짧고 얕은 역할 기반 경로 사용 |

외부 reviewer가 필요하다면 사용자 지정 Codex Reviewer를 사용한다. 문서상 owner approval은 사용자가 사전 승인했으나 플랫폼 보안·권한 절차는 우회하지 않는다. 이는 미달 결과를 통과 처리할 승인이 아니다.

## 8. 참고 아이디어와 불확실성

구체적인 알고리즘, 유형 체계, 단계 구성은 로드맵에서 선택한다. 예시 문장을 최종 정답으로 고정하거나 하나의 문장 틀을 모든 용도에 강제하지 않는다.

| 미확인 사항 | 영향과 알려진 단서 |
|---|---|
| 활용 정보 부족 241개의 근거 위치와 충분성 | 현재 blocks만으로 효과를 확정하지 못한 항목이 있다. 기존 source가 알고 있으나 누락한 관계인지 실제 미확정인지에 따라 필요한 작업이 다름 |
| 부재 121개의 의미 | 비대상·용도 근거 부족·공개 선택 문제 등을 구분해야 함. 부재를 무조건 채우거나 통과 처리하지 않음 |
| 조사 분류의 간결성·독립 용도 경계 | 양말 compact의 적절 판정 등 이견이 존재. 같은 내용을 더 짧게 묶을 수 있는지와 활용이 없어지는지를 구별해야 함 |
| 모든 기능·역할 조합의 적용 설계 | 일부 기능군 frame과 기존 나열 fallback이 공존. 새 기준 밖의 입력 처리도 다뤄야 함 |
| 실제 화면 적합성 | 오프라인 텍스트와 과거 B 통과만으로 새 후보의 글꼴·해상도·가독성을 확정할 수 없음 |

미확인 효과를 추측하지 않는다는 이유로 “복용할 수 있다” 같은 정보 부족을 해결 완료로 바꾸거나, 해결되지 않은 항목을 조용히 제외하지 않는다. 처리 결과와 한계를 보고해야 한다.

## 9. 완료 조건과 필요한 증거

아래는 결과 기준이며 각각을 독립 실행 Gate나 작업 디렉터리로 만들라는 요구가 아니다.

| 완료 조건 | 관찰 대상과 필요한 결과 | 한계 |
|---|---|---|
| C1. 전체에 적용되는 용도 선택 | 2,105개 전체의 기능·역할·조건 유형과 미처리 경로에 플레이어 관점 기준이 적용됨. 특정 기능군 이외에는 기존 전량 문장화로 돌아가는 해결이 아님 | 코드 변경 개수·재생성 개수만으로 증명 불가 |
| C2. 의미 보존과 설명 품질 | 네 표면의 실제 생성 결과에서 확인된 활용을 이해할 수 있고 불필요한 절차·추상화·내부 용어·반복이 정제됨. 툴팁은 간결하고 메뉴는 활용 차이를 설명함 | 1,599개 목록만 확인하거나 385개를 자동 통과시키지 않음 |
| C3. 전체 처리 결과의 설명 가능성 | 전체 결과와 부재·근거 부족·미확정의 처리를 구분해 대조 가능. 내부 사실을 보존하고 실제 공개 주장에만 근거를 연결. 미해결 결함은 완료로 위장하지 않음 | 결함 비율 감소나 임의 수치 목표가 완료를 대신하지 않음 |
| C4. 기존 제품으로의 일관된 공급 | KO/EN Tooltip/Menu가 교정된 동일 자료를 소비하고 기존 계층 책임을 유지. 필요한 기존 검사는 정확한 관련 명령 exit 0일 때만 PASS | 사용자 게임 확인 전 오프라인 구현 완료와 제품 최종 수락을 구분 |

필수 결과는 교정된 공통 규칙·관련 작업물, 실제 생성 설명, 전체 범위의 품질·잔여 사항을 판단할 수 있는 기록, 사용자 검토 가능한 기존 공급 경로의 후보이다. 형식과 중간 산출물은 로드맵에서 정하고 기존 항목별 자료를 활용할 수 있다. 증명만을 위한 추가 artifact는 필요하지 않다.

새 후보의 실제 Tooltip 네 물리적 줄과 Menu 가독성은 사용자 게임 관찰 없이 통과 선언하지 않는다. 기존 B 통과는 이전 후보에 귀속하며 새 품질 수락으로 확대하지 않는다. 이 문제의 완료가 release나 생태계 전체 재검증 완료를 뜻하지 않는다.

## 10. 입력 전달 전 확인

- 전체 2,105개 범위와 플레이어 관점의 용도 의미를 본문에 명시했다.
- A·1·2·3 및 B/C의 역할, 부분 교정과 미달 상태, 전수 수치의 의미·한계를 설명했다.
- 대표 사례는 결함을 설명하는 예시이며 수정 범위·고정 문안이 아님을 구분했다.
- 전체 적용과 실제 결과 확인은 요구하지만 단계 수·알고리즘·Gate 수·중간 artifact를 강제하지 않았다.
- 다음 원본 자료가 없는 작성자도 이 문서와 공통 문서로 로드맵을 설계할 수 있도록 핵심 근거를 요약했다.
