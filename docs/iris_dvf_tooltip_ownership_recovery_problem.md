# 문제 B — 검수된 DVF compact 공급과 네 줄 Tooltip 복구

## 현재 실행 기준 — v3 / 2026-09-11

**현재 상태: complete.** 사용자 실제 PZ 확인과 명시적 통과 지시로 B 구현·통합·실제 표시를 수락했다. 추후 설명 교정은 별도 후속 과제이며 C/current/release 완료는 아니다. [최종 수락 기록](iris_tooltip_supply_closeout.md)을 따른다.

현재 실행은 [v3 계획](iris_dvf_tooltip_s2_supply_ownership_recovery_plan.md)을 따른다. 입력은 `Iris/build/description/composition/descriptions.json`의 검수된 compact (`ba0fc047b3a613e7ef98d2d762cfbd10c1996a02ad4e6f96d1bffa61878262d0`)이며 같은 reader의 expanded가 C 인계점이다. r6 문장 fallback은 사용하지 않는다.

목표는 S1 소분류, S2 DVF compact 한 줄, S3 근거 있는 획득 장소, S4 유효한 레시피·우클릭·자유 조리 후보 하나를 Alt에서 화면 최대 네 줄로 표시하는 것이다. 기존 T1의 S3/S4 두 L4 행은 이 목표와 달라 후보 경로에서 수정한다. S1과 기존 support/admission은 보존하며 일반 strict finalization과 historical 자료는 별개다. 다중 wrap, clipping, 말줄임, 폰트 축소로 통과시키지 않는다.

현재 구현·검증 상태와 동일 후보 위치는 [실행 결과](iris_tooltip_supply_closeout.md)의 최신 기록을 따른다. 실제 PZ 미관찰은 자동 검증과 구분하고 current 공동 활성화 및 C 완료로 확대하지 않는다.

## 2. 문제 정의

### 현재 상태와 기대 상태의 차이

문제 A는 새 설명을 생산하고 offline 소비하는 데까지 완료했다. 이것만으로 기존 Tooltip의 S2에 새 설명이 나타나지는 않는다. 별도로, 이전 문제 6의 후보 경로는 DVF product가 Tooltip 전체와 Recipe 변형을 재발행하고 Layer 3 current에 연결하는 방식이었다. 사용자가 요구한 것은 기존 Tooltip의 3계층 설명 칸인 S2에 DVF 설명을 공급하는 것이며, Tooltip 전체 소유권의 이전이 아니다.

따라서 B는 **채택된 compact를 기존 Tooltip owner의 S2 입력으로 연결하고, 생산·저장·설치·선택 경로에서도 Tooltip과 Recipe의 책임을 유지하는 것**이다. 기존 S1/S3/S4와 Alt·줄바꿈·상호작용 선택 동작이 잘못됐다는 전제에서 출발하지 않는다.

### 영향과 필요성

현재 r6가 있어도 제품 연결 전에는 사용자가 그 복구 효과를 Tooltip에서 얻을 수 없다. 이전 후보의 결합을 그대로 사용하면 Layer 3 갱신이 Tooltip/Recipe 전체 공급과 선택을 지배한다. 이는 확인된 책임 경계 문제이며, 실제 게임에서의 장애 빈도나 설치 상태는 미확인이다. A가 해결한 내용 복구와 B가 해결할 공급·제품 통합을 구분해야 한다.

## 4. 목표

- r6 compact가 기존 Tooltip의 정식 S2 공급 경로를 통해 표시된다. 후보 파일 생성만으로 연결 완료라고 하지 않는다.
- Tooltip 조립·static·Recipe 변형·활성 선택의 책임이 기존 Tooltip 경로에 있고, DVF product가 전체 payload와 선택 지점을 지배하지 않는다.
- 생성부터 패키징·조회까지 같은 경계를 유지하며 다른 슬롯과 기존 사용자 동작을 보존한다.
- C가 사용할 expanded와 같은 채택 설명 자료를 추적할 수 있다. 같은 자료를 쓴다는 이유로 양쪽 전체 제품을 단일 DVF owner에 묶지 않는다.
- 실제로 다룬 소비 경로에서 설명 자료의 정상 소비와 필요한 결과 문서 갱신을 양립시킨다.

공급 API, 직렬화, 선택 지점의 구현, 작업 순서와 파일 배치는 로드맵에서 정한다. r6 문장의 길이를 줄이려고 Tooltip 동작을 바꾸거나 소비자가 의미를 재요약하지 않는다. 실제 내용 결함이 드러나면 해당 설명 생산 책임에서 최소 정정하고 같은 정정 자료를 B/C에 사용한다.

## 5. 대상, 책임 경계 및 범위 밖

### 포함 대상

S2 입력·lookup·자료 생성/선택 연결, Tooltip/Recipe를 DVF 소유로 만드는 후보 생산·설치·패키징 결합, 관련 계약·검사의 잘못된 전제 및 제품 반영 상태의 정확한 보고가 대상이다. 목표 달성에 필요한 기존 Tooltip 경로의 최소 수정은 허용한다. 모든 기존 코드를 무수정으로 둘 의무는 없다.

A의 `load_adopted → load_candidate → consume_candidate`는 과거 `audit.inputs`를 현재 파일 경로에서 다시 읽는다. 설명 문서인 ARCHITECTURE를 갱신하면 해시가 달라 정상 소비가 거부됐고, 문서를 원본으로 복원하고 추가 설명을 기존 closeout으로 옮겨 소비를 복구했다. 이 결합은 단순히 “모든 문서를 영구 동결한다”는 방식으로 해결하지 않는다. B가 공통 소비 경로를 먼저 다루면 정확한 채택 자료 검증과 과거 생산 재현의 책임을 구분하는 최소 해결을 함께 다룬다. C가 먼저 해결한 경우 재사용한다. 전체 재현 시스템 재설계는 요구하지 않는다.

### 범위 밖

- 기존 슬롯 수·폭에 따른 줄바꿈·Alt 동작의 재설계. “최대 4줄”과 logical slot의 표현 차이를 새 결함이나 새 줄 수 정책으로 만들지 않는다.
- A의 전수 조사 재실행, 남은 4,223개 claim의 전수 해결, 공백 0개 만들기.
- C의 Menu 표시 구현, Layer 4 Recipe/우클릭 의미의 DVF 이전.
- 사용자 게임 설치·Workshop 공개·배포를 이 문제 문서만으로 실행하는 것.

후속 실행 환경은 Windows/PowerShell이며 runtime은 Lua다. 실제 PZ 확인 환경은 계획에서 확인한다. 개발 산출물의 정상 소비와 실제 설치/릴리스 주장을 구분한다.

## 6. 선행 조건과 의존 관계

A의 r6는 확보된 입력이며 모든 질문 resolved를 기다릴 필요가 없다. B와 C는 같은 설명 자료를 사용하지만 어느 한쪽의 전체 구현을 다른 쪽의 착수 조건으로 만들지 않는다. 공통 소비/버전 결속은 한 번 해결하고 공유한다. 작업의 순서와 묶음은 실제 인터페이스 의존성에 따라 정한다.

r6는 출발 기준이지 향후 정정 불가능한 영구 버전이 아니다. 필요한 생산/계약 수정이 있으면 기존 r6와 PASS를 보존하고 정정된 실제 대상에 필요한 검증을 귀속한다. 옛 PASS를 바뀐 코드·자료에 자동 적용하지 않는다.

| B2. 실제 내용과 기존 동작 보존 | 전체 공급 대상의 대응·정상 부재·오류가 구분되고, 실제 KO/EN Tooltip 결과에서 새 S2와 기존 슬롯/Recipe/Alt 동작을 함께 확인한다. 복합 용도·정상 공백·대상 밖 사례 등 위험을 대표하는 사례는 계획에서 선택한다. |
| B3. 후속 소비 가능성과 정확한 완료 범위 | C가 같은 자료를 사용할 수 있고 정상 소비가 가변 설명 문서의 일반 갱신 때문에 다시 깨지지 않는 경계를 확보한다. 실제 연결/선택 상태와 미검증 게임·배포 범위를 보고한다. |

세 조건은 세 개의 별도 Gate를 만들라는 뜻이 아니다. 기존 관련 검사를 재사용하고 같은 입력·결과의 확인을 묶는다. 새 정규 validator, proof/seal tree, gate별 workspace, A의 전체 장시간 검사 반복은 요구하지 않는다. 실제 변경·실패에 필요한 검사만 수행하며, 도구 미확보를 PASS로 보고하지 않는다. 계약·결과 문서는 실제 책임과 완료 범위를 반영한다.

## 10. 입력 전달 전 확인

A 완료와 제품 미연결, 정상 공백과 통합 오류, 기존 UI와 잘못된 생산 책임, 공통 소비와 전체 제품 소유를 구분했다. r6 수치는 통합 입력 기준이며 신규 달성 할당량이 아니다. 원본 경로 열람 없이도 목표·책임·한계·완료 조건을 알 수 있도록 설명했고 구현 수단·단계 수·검사 수는 고정하지 않았다.
